# Frozen camera preview contention diagnostic

28 October 2026. Production remains `872c9f7`, compiler9, readiness50/100. The actual CameraX probe measured1.295FPS on the owned API35 emulator, much slower than isolated static native calls. Native graph recreation is not the observed explanation. This experiment tests whether concurrently bound Preview use-case work contributes to that slowdown, without changing pose fidelity or rep evidence.

Run four fresh instances of the byte-identical app in fixed **A B B A** order: A is the unchanged activity's Preview+ImageAnalysis binding; B unbinds/rebinds that same activity's existing ImageAnalysis use case alone. The research instrumentation accesses the frozen owned fields explicitly; no main code, UI flow, CameraX settings, resolution selector, image conversion, model or thresholds change. All rebindings execute on the main thread, following the [CameraProvider API](https://developer.android.com/reference/androidx/camera/lifecycle/ProcessCameraProvider). CameraX can choose streams differently when use-case combinations change; record actual prepared input dimensions and original frames, and never assume pixel identity.

Each block first requires three delivered camera results, selects its fixed binding, then warms for15 seconds and records45 seconds. Keep all warmup and measurement callbacks. Preserve original capture/arrival/result times, native durations, reset/recreation counters, model SHA, dimensions, raw pose status, PSS and errors. Save one lossless original camera frame and complete raw33-point result at the first delivered result at or after20 seconds. Synchronous export cost remains in observed delivery; exclude no slow frame.

Additionally record [Debug.threadCpuTimeNanos](https://developer.android.com/reference/android/os/Debug), owner thread ID and priority at callback entry. Differences describe the same analyzer thread's **callback-to-callback** CPU use, including intervening work. They do not isolate native inference or conversion CPU, measure all native worker threads, or replace wall durations. Unsupported/nonmonotonic/thread-changing measurements remain unassessable; report CPU support explicitly. Do not relabel wall residual as a specific component's cost.

Freeze source, fixture, APKs, runner and API35 runtime identity before execution. Compare all four blocks and inspect all four original inputs/raw results. Report variation and prepared dimensions. A difference is evidence about this ablation on this host, not proof of one universal root cause. If no consistent speed effect appears, retain that failure and do not remove the product preview. No new human labels, skeletal holdouts, raw-MP33 rewriting, app optimization or APK delivery occurs here.
